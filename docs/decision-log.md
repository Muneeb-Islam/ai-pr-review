## Phase 15 decisions (2026-10-05)

| #   | Topic                           | Decision                                                                                                                                                                                                                                                                                                                                                                                    | Status  |
| --- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| 84  | Row-level security is adopted   | The phase file said to adopt it if the worker's system access survives. It does: the worker and webhook pool announce `aipr.scope = system` on every connection, the dashboard's handlers run in a transaction that names only the user's installations. It protects against a query that forgets its scope, not against code that already runs SQL, and it needs a role that is not a superuser, has no `BYPASSRLS` and does not own the tables (the stack creates `aipr_app`; a start-up check and a metric report it). The api's whole test suite runs on that plain role. | Assumed |
| 85  | Installation access follows repositories | A viewer's access to an installation-level page needs at least one repository of it that the user can still reach, so removing someone on GitHub removes the installation pages as well as the repositories within the cache lifetime. Admins are still verified by their organisation role.                                                                                          | Assumed |
| 86  | Uninstall and suspend           | Uninstall: the status changes first, queued and running runs are cancelled with a reason, provider keys and access caches are deleted at once, history is purged `RETENTION_DAYS` after the change. Suspend: runs are cancelled, nothing else is deleted (reversible), and a suspended installation is never purged. The key is deleted early because a secret has no use once the App is gone.                       | Assumed |
| 87  | Limits are decided in the run's transaction | The daily quota and the queue-depth limits are checked inside the transaction that creates the run, under a lock per installation, so 200 concurrent events cannot all pass a limit of 100. A refused run is a visible `skipped` run (`quota_exceeded`, `queue_limit`). The cost is that run creation of one installation is serialised for the length of two count queries.                          | Assumed |
| 88  | Webhook rate limits             | Per client address (generous: GitHub uses few), per bad signature (429 after the limit) and per installation (429, and the delivery is not recorded so a later redelivery is processed). A 429 is preferred to a silent drop: the sender sees it and no run is lost without a trace.                                                                                                        | Assumed |
| 89  | Fork caps are constants         | Fork review (opt-in) is capped at 15 files, 40,000 characters, 8 inline comments, 8 requests and 120,000 tokens per pull request, applied where the context is collected, lowering a limit and never raising one, with a visible warning. The numbers are code (`FORK_PR_LIMITS`), not settings, so a repository cannot loosen them.                                                          | Assumed |
| 90  | Registered secrets are masked everywhere text leaves | `registerSecret` values (and the password of every connection string) are masked by `redactSecrets` in prompts, comments and stored findings, whatever their format. Known token formats were already covered; the platform's own secrets (a database password, a custom key) were not.                                                                                  | Assumed |
| 91  | Secrets as files                | `NAME_FILE` supplies `NAME`, for names the schema knows only (an unrelated `*_FILE` in the environment must not fail a start-up). The production stack passes every secret that way, so no secret is in the image, the Compose file or `docker inspect`.                                                                                                                                     | Assumed |
| 92  | Production topology             | One public origin: nginx serves the build and proxies `/api`, `/auth`, `/webhooks` to the api (the cookie, CSRF and CORS rules assume one origin). TLS is terminated in front of it by the operator. Only `web` publishes a port; `/metrics` is scraped inside the network. The Compose project has its own name so it can never replace the development containers.                    | Assumed |
| 93  | Metrics                         | Gauges are computed at scrape time from PostgreSQL, BullMQ and a Redis hash (the GitHub rate-limit headers, written by the api and every worker), so they are the same whichever replica answers and survive restarts. The endpoint needs a bearer token and does not exist without one; it names no tenant.                                                                              | Assumed |
| 94  | Backups                         | `pg_dump` custom format with `--no-owner --no-privileges`; restoring re-applies the application role's grants (a drill found that without them the api cannot read its own tables after a restore). Redis is not backed up. The encryption key is backed up separately from the dumps.                                                                                                       | Assumed |
| 95  | Chaos checks are a separate suite | They need Docker, take minutes and destroy containers, so they run with `npm run test:chaos` (weekly and on `main` in CI), not with `npm test`. They use real separate worker processes and require every run to end exactly once.                                                                                                                                                         | Assumed |
| 96  | Installation sync is careful    | An installation GitHub reports as gone is uninstalled by the sync, except when more than two and more than half of all look gone at once (probably the wrong App credentials): then nothing is changed and an error says why. Uninstalling deletes keys, so a false positive is worse than a late one.                                                                                   | Assumed |
| 97  | Retention of bookkeeping        | Audit entries 365 days, webhook delivery records 14 days, access caches 30 days (or twice the session lifetime when that is longer). Runs and findings stay at `RETENTION_DAYS` (90).                                                                                                                                                                                                       | Assumed |
| 98  | Emergency revocation            | `credentials:revoke` deletes stored provider keys (all, or one installation's). It does not replace revoking at the provider, which comes first; it makes sure the platform stops using a key that may be exposed.                                                                                                                                                                         | Assumed |
| 99  | Backend bundles needed a banner | The esbuild bundles of the api and the worker did not start (a bundled CommonJS dependency calls `require` for a Node module, which an ES module does not have). Found when the production image was first run; fixed in `scripts/build-node.mjs`, and CI now starts both bundles.                                                                                                      | Fixed   |

## Consequences worth remembering

- **Fork safety changes shape.** The old Action had to avoid secrets on forks. The App holds keys on the server and never executes PR code, so fork review is technically safe. The remaining risks are cost abuse and prompt injection from strangers, handled by opt-in plus quotas.
- **Config from the base branch only.** A PR author must not be able to change review instructions, provider or `base_url` through the PR itself.
- **`base_url` is an SSRF surface.** Dashboard-only, HTTPS only, private and link-local addresses rejected.
- **Coverage depends on CI.** If the artifact is missing at review time, coverage is reported as "not measured". A later `workflow_run` re-evaluation is a stretch goal (Phase 11).
- **Visible `skipped` runs.** Guard decisions create a run with a reason so users can answer "why wasn't my PR reviewed?".

## Provider notes (DeepSeek)

- **API shape:** OpenAI-compatible chat completions at a configurable base URL.
- **Structured output:** JSON mode, no strict schema enforcement. Every response is validated by our schema with one repair retry (adapters in Phase 6, validation and the repair retry in Phase 7).
- **Model IDs:** configuration only. Checked against DeepSeek's documentation in Phase 6 (October 2026): `deepseek-flash` and `deepseek-v4-pro`; the older `deepseek-chat` and `deepseek-reasoner` are no longer listed. Re-check before release, the names change.
- **Privacy:** the hosted DeepSeek API is operated by a China-based company. State this in the dashboard (provider selection screen), README and `docs/privacy.md`, and log which provider receives code. Users who cannot accept it choose another provider.
- **Rate limits and latency:** can be spiky; rely on retry, backoff and the concurrency limiter.
